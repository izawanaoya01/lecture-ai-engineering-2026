## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified ）の問題を、難しさの違う 3 件読んだ。作成と検証の手順を、OpenAI のブログ「Introducing SWE-bench Verified」（https://openai.com/index/introducing-swe-bench-verified/ ）と元の SWE-bench の論文（arXiv 2310.06770）で調べた
  - 最初は基礎（rubric の「根拠」に、ヒント・範囲の内容を持ち込まない旨を 1 行足して再採点）に取り組んだが、採点モデルが 503（混雑）で 1〜2 件目から失敗し続けたため、発展に切り替えた（`lectures/04/homework/rubric_grounding.md` は未実行）
- 結果：
  - 読んだ問題（1 件 = GitHub の issue、実際の修正、採点用のテスト）
    - `django__django-11099`（15 分未満）
      - 内容：ユーザー名チェックで、末尾の改行を通さないようにする（正規表現の `$` が末尾の改行にもマッチする）
      - 自分なら：ちょっと調べればすぐできそう。解き方も issue に書いてある
      - LLM にとって：すぐできるし、解き方が書いてあるので間違えにくい。受け入れ条件も簡潔で明確で、特に難しいポイントはなさそう
    - `astropy__astropy-12907`（15 分〜1 時間）
      - 内容：入れ子にしたモデルで依存関係の行列が誤る、関数のバグ修正。issue には症状だけで原因は書かれていない（実際の修正は 1 語）
      - 自分なら：調べたらできるかもしれないが、無理そう
      - LLM にとって：直すポイントが明確でないので難しいかもしれない。受け入れ条件は示されていないが、文章を読み解ければテストケースを作って改善できそう
    - `astropy__astropy-14369`（1〜4 時間）
      - 内容：天文学データ（CDS 形式）の読み込み時に、単位の表記が崩れる。原因は単位を解析する文法の割り算の結合の向きで、修正では文法と自動生成のパーサーのファイルを書き換えている
      - 自分なら：できなさそう。このドメインがよく分からず、単位のずれが文法の結合の向きによることを見つけられなさそう
      - LLM にとって：再現用のものがあるのは良いが、どのような結果になるべきかという点と、原因が症状から離れている点が難しそう。issue の文脈に流されると見つけにくい。生成ファイルも見なければならない点も難しそう
  - 作成と検証の手順
    - 元の SWE-bench：人気の Python リポジトリ 12 個から PR を約 90,000 件集め、「issue を解決している」「テストを変更している」「直す前は失敗し直した後は通るテストがある」で自動的に絞り込んで 2,294 件
    - Verified：Python の経験があるソフトウェア開発者 93 人が、テストセットから無作為に選んだ 1,699 件を、1 件ごとに別々の 3 人で確認した。確認したのは、issue の説明が足りているか、テストが正しい解き方を誤って落とさないか、その他の大きな問題、難しさ（直すのにかかる時間）。各項目 0〜3 で、3 人のうち最も厳しい評価が 2 以上なら除外した。説明不足で 38.3%、不公平なテストで 61.1%、全体で 68.3% を除外し、500 件になった
    - 採点：モデルの修正を当て、FAIL_TO_PASS（直ったか）と PASS_TO_PASS（ほかを壊していないか）のテストが全部通れば解決。LLM による採点は無い
  - 今日の評価セットとの違い

    | | 今日の評価セット | SWE-bench Verified |
    |---|---|---|
    | 規模 | 10 件 | 500 件（1,699 件を検証して絞り込み） |
    | 作り方 | 講師 1 人が、エッジケースと仕込んだ失敗を混ぜて作成 | 実際の GitHub の issue と PR から自動で収集 |
    | 検証の人数 | 講師 1 人のラベル（受講者が自分のラベルと比べる） | 開発者 93 人、各件 3 人 |
    | 意見が割れたとき | LLM が unsure にした項目を人が見る。人同士の違いは残る | 3 人のうち最も厳しい評価を採り、問題がありそうなものは落とす |
    | 採点 | 人と LLM（T / F / unsure）。回の表示だけコード | テストの実行だけ |

- 気づき・疑問：
  - 1,699 件のうち 68.3% を除外していて、公平さのためには必要だと思うが、3 人のうち 1 人でも問題ありとすれば落とすのは厳しいと思った。少しでも問題があると重大なリスクにつながるものなのか、そうでないのかなど、その問題がどのような問題かによって変えてもよいのではないか
  - SWE-bench はテストで採点するので LLM 採点のゆらぎは無いが、そのテストが公平かを人が確認している。テストの確認は抜け漏れをなくすような作業なので、大変そうだと思った
  - `astropy__astropy-14369` では、issue に書かれていない挙動（`km/s.Mpc-1` をエラーにする）までテストされていた。3 人の確認で問題ないとされたのか、見落とされたのかは、その状況や問題を知らないと判断できず、よく分からなかった（疑問）
